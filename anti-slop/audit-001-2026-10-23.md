# Audit 001: More ("Lainnya") hub

- **Date:** 2026-10-23
- **Scope:** `MoreRoute` / `MoreHubColumn`, `app/src/main/java/id/umkm/pos/pro/ui/more/MoreRoute.kt`
- **Mode:** antislop AFTER (audit only, no source changes)
- **Direction source:** `docs/prd.md` §4, §5, §6.5. No `DESIGN.md` exists in the repository.
- **Declared dials:** ENERGY 1 / RHYTHM 1 / MOTION 1. The PRD asks for a restrained productivity tool, so a low dial is correct. The findings below are not a request to add decoration; they are about hierarchy, grouping, and states inside that restraint.

## Evidence

Captured from the running debug build, not from mockups.

- `anti-slop/evidence/2026-10-23/01-phone-font-100.png` (1080x2340, 450dpi, font scale 1.0)
- `anti-slop/evidence/2026-10-23/02-phone-font-135.png` (same device, font scale 1.35)
- `anti-slop/evidence/2026-10-23/03-tablet-two-pane.png` (2560x1600, 400dpi, two-pane path)

The device font scale was set to 1.35 for one capture and restored to 1.0 afterwards. Nothing was installed, removed, or cleared.

## Verdict

The screen is functional and accessible, but it has no hierarchy. Five equally weighted blocks compete for the same attention, so the eye has nowhere to land. Every block is a bordered card with the same radius and padding, which makes a navigation hub read as a stack of unrelated widgets. That is the concrete reason it feels flat and not premium.

The problems are structural, not cosmetic. Restyling the cards would not fix them.

## Findings

### HIGH (Hard Gate or mandatory PRD contract)

**1. Tablet split view opens with a sub-destination already selected, which makes the store card a dead control.**
- Rule: R-26, R-27. PRD §4.2 ("Keep the current destination visually obvious").
- Evidence: `MoreRoute.kt:116` uses `val selectedPane = activeDetail ?: MoreDestination.SETTINGS`. `03-tablet-two-pane.png` shows "Pengaturan" bordered and tinted green on first entry, while the user is on "Lainnya".
- Second symptom: `StoreIdentityHeroCard` navigates to `SETTINGS` (`MoreRoute.kt:234`), and `SETTINGS` is already the selected pane, so tapping the card on tablet produces no visible change at all.
- Why it matters: the app tells the user they are somewhere they did not go, and one of the two largest controls does nothing on that layout.

**2. A failed shift summary looks like loading, forever.**
- Rule: R-27. PRD §5.1 (clear states).
- Evidence: `MoreRoute.kt:87-102` sets `expectedCash` to `null` on `AppResult.Failure` and on any exception, and `MoreRoute.kt:341` renders `expectedCash?.let(Rupiah::format) ?: strings.shiftSummaryLoading`. There is no error branch, no retry, and the exception is swallowed.
- Why it matters: a database error is indistinguishable from a slow load. The cash figure is financial information, so a permanent "Memuat..." is worse than an error, because it looks like progress.

**3. The destructive demo label is clipped at 135% font scale.**
- Rule: R-03. PRD §5.3 (font scaling to 135% without clipping).
- Evidence: `02-phone-font-135.png` shows the button reading "Hapus" instead of "Hapus Demo". `DemoDataSection.kt:150-152` sets `maxLines = 1` with no `overflow` on a `Modifier.weight(1f)` button, so the text truncates silently.
- Why it matters: at the largest supported scale the destructive action loses the word that says what it deletes.

### MEDIUM (Purpose-Gate: technique or structure without a stated purpose)

**4. Five bordered cards turn a hub into card soup.**
- Rule: R-05, R-14. PRD §5.1 ("avoid putting every item in a separate bordered card").
- Evidence: store card, shift card, two `MenuListRow` surfaces and the demo card all use `shape = large` (16dp), a 0.75dp border, and 16dp padding. Gaps are 8dp (`MoreRoute.kt:228`).
- Why it matters: when everything is a card, nothing is a group. The PRD already prescribes the alternative: thin dividers only where they clarify grouping.

**5. No focal point and no section structure.**
- Rule: R-20, R-31. C-3 (content-driven composition).
- Evidence: store identity, live shift, settings navigation, customer navigation, and a developer tool all carry the same visual weight. There is no section label anywhere on the screen.
- Why it matters: the user must read all five blocks to know what the screen offers. A More hub should be scannable in two seconds.

**6. The store identity color is generated from the store name hash, not from the brand palette.**
- Rule: R-29. C-1 (intentionality).
- Evidence: `StoreIdentityHeroCard` reuses `ProductThumbnail` (`MoreRoute.kt:399`), whose `thumbnailTone` picks one of six palettes from `abs(seed.hashCode()) % 6` (`ProductThumbnail.kt:81-110`). "Toko Pookie POS" lands on bucket 1, royal blue, which appears nowhere else in the app.
- Why it matters: renaming the store can turn the brand block violet or rose. The one element that should express ownership is the least controlled color on the screen.

**7. One icon carries three different meanings.**
- Rule: R-04. PRD §5.2 ("use icons to help scanning").
- Evidence: `ic_users` is the shift badge (`MoreRoute.kt:303`), the "Ganti kasir" action icon (`MoreRoute.kt:357`), and the customers row badge (`MoreRoute.kt:253`).
- Why it matters: the icon stops distinguishing "people who operate the till" from "customers who owe money", which are different jobs.

**8. Two controls lead to the same place with different affordances.**
- Rule: C-1. PRD §4.2.
- Evidence: the store card (`MoreRoute.kt:234`) and the "Pengaturan" row (`MoreRoute.kt:248`) both open `MoreDestination.SETTINGS`. The card's chevron implies it opens the store profile, which it does not; the profile is two taps deeper.
- Why it matters: the user learns the wrong mental model on the first tap.

**9. The loudest element on a navigation hub is an occasional operational action.**
- Rule: R-15. PRD §5.4 ("one prominent primary action per screen").
- Evidence: "Ganti kasir" is a filled primary button (`HeaderActionButton`, `ScreenHeader.kt:113`) inside the middle card, while the actual purpose of the screen, choosing a destination, has no emphasis at all.
- Why it matters: it makes the hub feel like a dashboard with a random CTA attached.

**10. A developer-only tool wears the brand accent and the same weight as real features.**
- Rule: R-14, R-15, R-38.
- Evidence: `DemoDataSection` renders a full card with a primary-tinted `ic_flask` badge and two large outlined buttons, in the same stack as production settings. It is correctly gated by `BuildConfig.DEBUG` (`DemoDataSection.kt:57`), but nothing in the UI says it is a debug tool.
- Why it matters: in a debug build a merchant or tester cannot tell the sandbox from the shop's data, and "Hapus Demo" is the second most prominent action on the screen.

**11. Loading state flashes placeholder identity as if it were real data.**
- Rule: R-27, R-38.
- Evidence: `settings` starts at `null` (`MoreRoute.kt:79`) and `StoreIdentityHeroCard` falls back to `moreDefaultStoreName` = "Toko Pookie POS" and `moreDefaultCashierName` = "Kasir Utama" (`MoreRoute.kt:376-385`). `customers` starts as an empty list, so the badge shows "0 Data".
- Why it matters: on a cold start the screen briefly shows a store name that is not the user's store. A loading placeholder should look like a placeholder, not like content.

**12. The tablet hub column is a hard-coded 360dp.**
- Rule: R-03. PRD §5.5 ("Do not hard-code major screen widths").
- Evidence: `MoreRoute.kt:127-129` sets `.width(360.dp)`.
- Why it matters: on a 1024dp window the hub consumes a fixed third and cannot adapt to font scale or window resizing, which the PRD makes mandatory.

### LOW (Quality Locks)

**13. "0 Data" is a meaningless count and generic wording.**
- Rule: R-16, R-31. PRD §5.1 (clear empty states).
- Evidence: `IdStrings.kt:707` `"$count Data"`; visible as "0 Data" in `01-phone-font-100.png`.
- Better: when the count is zero, say what the state means ("Belum ada pelanggan"); when it is not, show what the owner acts on ("3 pelanggan, 1 kasbon").

**14. The header repeats the tab label and orients nobody.**
- Rule: C-3, R-20.
- Evidence: `MoreRoute.kt:216` `ScreenHeader(title = strings.navMore)`, while `navMore` and `moreHubTitle` are both "Lainnya". `ScreenHeader` supports `supportingText` and this screen passes none.
- Why it matters: the one line that could say "Toko, staf, dan data" is spent repeating the navigation bar.

**15. The parent hub is less informative than its child hub.**
- Rule: R-05, C-3.
- Evidence: every row in `SettingsHubColumn` has a description and a live status badge (`SettingsScreen.kt:227-300`), while the More rows have a title only, and only one row has a badge.
- Why it matters: the higher-level screen should help prioritize; here it forces a tap to learn anything.

**16. Badge and chevron alignment drift on the customer row.**
- Rule: C-1.
- Evidence: on that row the badge sits under the title (`MenuListRow.kt:95-100`), so the row is taller and the chevron centers against the full height, while the other rows center against a single line. Visible in `01-phone-font-100.png`.

**17. Border, shadow, and radius are stacked on every surface.**
- Rule: R-11, R-12.
- Evidence: `PosCard` applies a 0.75dp border plus `shadowElevation = 0.5.dp` plus a 16dp shape (`PosSurfaces.kt:37-45`); `MenuListRow` repeats the same recipe.
- Why it matters: elevation is supposed to mark what rises above the page. When every block has the same faint lift plus a border, the effect is noise rather than hierarchy.

**18. Spacing has no rhythm.**
- Rule: R-05.
- Evidence: 8dp between cards, 16dp inside them, 16dp screen margin, and the same arrangement at every level. There is no larger gap between logical groups because there are no logical groups.
- Why it matters: whitespace is the only tool that can separate "my shop" from "settings" here, and it is used uniformly.

**19. Three unused More strings remain in the string contract.**
- Rule: not an antislop rule; code hygiene.
- Evidence: `moreHubTitle`, `moreHubLanguage`, and `moreHubPrinter` have no usage outside the string interfaces.
- Why it matters: they suggest an intended More design that the screen never implemented, which makes later work harder to reason about.

## What passes

- **Contrast (R-25):** measured on the shipped palette, every pair used on this screen passes WCAG AA. `#52605B` on `#FFFFFF` = 6.6:1; on `#F6F8F7` = 6.19:1; white on `#0D5C46` = 7.97:1; chip text on `#EEF2F0` = 5.84:1; warning `#B45309` on `#FEF3C7` = 4.51:1; danger `#DC2626` on white = 4.83:1. The unused `TextMuted` token would fail at 3.74:1, and it is not used on this screen.
- **Copy (R-02):** no em dashes and no decorative emoji.
- **Controls (R-26):** every visible control has a real handler in code. The only exception is finding 1, which is layout-specific.
- **Fabricated content (R-17, R-18, R-36):** none. Counts and cash come from repositories.
- **Icons (R-04):** one icon family (Material), no emoji, no sparkles. The problem is reuse, not the set.
- **Theme (R-21, R-34):** light theme only, as the PRD requires; there is no broken second theme.
- **Motion (R-19):** none, which matches MOTION 1. Do not add animation to fix the flatness; the missing ingredient is information hierarchy.
- **Touch targets (R-03):** card rows and buttons meet 48dp.
- **Layout integrity at 135%:** no overlap, no horizontal overflow, no clipped card. Only the button label in finding 3 truncates.

## Not verified

- TalkBack and D-pad focus order were not exercised on a device. Accessibility claims above come from reading the semantics setup (`clickable`, `Role.Button`, content descriptions) and from the rendered hierarchy dump.
- The 135% capture covers the phone layout only. The tablet path was captured at 100%.
- No control was activated except the "Lainnya" destination, to avoid mutating the emulator's data.

## Suggested fix direction (not implemented)

The smallest change that addresses the root cause, in order:

1. Collapse the three navigation blocks (store, settings, customers) into one grouped surface with section labels and dividers, keeping the store plus shift as the single hero.
2. Give the hero a real focal role: store identity in brand color, active operator, shift duration, expected cash with a proper error state, and one primary action.
3. Replace the hash avatar with a brand-owned identity mark, or drop the avatar entirely.
4. Make the tablet default an explicit empty detail state instead of auto-selecting Settings, and replace the fixed 360dp column with a weighted or clamped width.
5. Isolate the debug section behind a neutral "Debug tools" label, or move it into Settings.
6. Fix the 135% truncation by allowing the demo buttons to wrap or to become full-width stacked actions.
